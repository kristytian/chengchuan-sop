# 依赖图模块：功能与用户流程

状态：**已定稿**（第 2 步 · 依赖图，2026-11-03；4 个待判断问题已按建议定下，见文末）
补充：2026-11-04 第 3 步线框后，增加「首次导入 / 日常维护」两种模式。
对应旅程：时刻 1「QA 面对一大批引用，凭什么敢点『确认』」（design/journey-scenario1.md）

## 目的

让 QA 在不离开界面的前提下，把导入时识别出的引用关系逐条确认到「敢拿它当依据」，并处理导入时发现的问题。影响清单、换版追踪都建立在这些已确认的引用上。

**使用者：** QA 文件管理员。待确认清单只对 QA 可见。

## 已定的三条（来自你的回答）

1. 高置信的**先批量通过**，低置信的**再逐条看**。
2. **需要**独立的导入进度界面。
3. 「谁引用了我 / 我引用了谁」的双向视图，**独立页和侧栏两种都做，用户测试时比较**。

## 两种模式（第 3 步线框后补充，见 UX-26 到 UX-28）

| | 首次导入 | 日常维护 |
| --- | --- | --- |
| 什么时候 | 刚上线，把整个文件库一次读进来 | 之后每有一份新版本批准入库，或有文件作废 |
| 量 | 很大：样本 35 份就有 196 条引用；真实药厂的文件量远比这多 | 很小：这一份文件里的几条引用，加上牵涉到它的其他文件 |
| 工作单位 | 一批引用（按「可批量 / 需逐条看」和原因分组） | 一份文件 |
| 用哪种界面 | **导入向导**：先批量通过高置信的一批（先抽查）；需要逐条看的，点进去落到按文件阅读的原文视图，定位到那一句 | **按文件阅读的工作台**（第一轮方向 2）：打开这份文件，引用在原文句子里高亮 |

**跨文件事件的队列：** 两种模式都会遇到「一件事分散在多份文件里」的情况，用按原因分组的队列（第一轮方向 1 的长处）作为提醒入口，点进去同样落到原文视图。例如：
- 一份文件作废了，所有引用它的文件都要处理（如 SOP-SC-028 被 SOP-SC-035 替代）。
- 一个编号指向不明，出现在多份文件里（如 SMP-WJ-004 在 4 份文件里出现 8 次），选一次答案可以套用到全部，但逐条列出、可取消。

**原型要演示日常维护：** 场景一的修订版 SOP-SB-021-03 在换版追踪里「标记新版已批准」之后入库，回到依赖图确认这份新版本的引用，四个模块首尾相接，形成闭环。新版本里哪些引用可以沿用上一版的确认、哪些要重新确认，第 4、5 步再定。（第三轮线框的提议见 UX-30。）

**已作废文件：** 默认隐藏，开关写「显示已作废文件（n）」，想看再点出来（UX-27）。

**单份文件的双向依赖：** 不画全库的关系图，只画一份文件的上下游。两种画法在比较：左右对称图、分组列表（design/wireframes/dependency-graph-r2-two-way.html）。

## 页面清单（共 5 个）

| # | 页面 | 它要回答的问题 | 主要动作 |
| --- | --- | --- | --- |
| 1 | 依赖图首页 | 导入了吗？确认到哪了？还剩什么？ | 开始导入；进入确认队列；进入待确认清单 |
| 2 | 导入进度 | 系统在读什么？读到了什么？ | 看进度；看结果摘要；进入确认队列 |
| 3 | 引用确认队列 | 哪些可以放心批量过？哪些必须我亲自看？ | 批量确认；逐条确认、驳回、改指向；筛选 |
| 4 | 单份文件的双向依赖 | 这份文件引用了谁？谁引用了它？它在哪个文件组？ | 切换方向；点进被引用的文件；查看原文条款 |
| 5 | 待确认清单 | 导入时发现了哪些问题？我处理到哪了？ | 标为已处理；暂缓（要写理由）；按类型筛选 |

## 主流程（QA）

1. 打开依赖图，看到首页空状态：还没有导入。点「开始导入」。
2. **导入进度：** 依次读取文件 → 切分条款 → 对照台账 → 识别引用 → 发现问题，最后给出结果摘要（见下表）。点「去确认引用」。
3. **批量通过：** 先看到「可批量通过」那一组。可按文件或类型浏览、抽查几条的原文，确认没问题后一键通过。
4. **逐条处理：** 再处理「需要逐条看」的那一组：看原文和系统的理由，选确认、驳回或改指向。
5. **处理待确认清单：** 对每条问题标「已处理」，或「暂缓」并写理由。
6. **随时查看单份文件的双向依赖**，用来验证「我确认对了吗」。
7. 全部确认后，首页显示完成，提示可以去影响清单。

**补充（2026-11-04，UX-35、UX-37）：** 整体结构改为「文件库、变更」两个空间，这个模块在界面上叫「文件库」。文件库首页是一张文件列表，左边按状态、类别、起草部门、标记分类；「文件」「待处理」「入库核对」是文件库的子页。线框见 design/wireframes/dependency-graph-r4.html。

**补充（2026-11-04，UX-33）：** 上面第 5 步「处理待确认清单」不再是导入向导的一步。导入向导只管确认引用（① 导入 → ② 批量通过 → ③ 逐条看），做完就可以去影响清单；问题（现在叫「待处理」，按根源分组）是一份长期清单，从首页进入，可以分批处理。首页只放这两件事。

## 批量规则（已定）

**可批量通过：** 满足以下全部条件的引用——高置信、能唯一指向库里一份文件或一条通则、没有牵涉待确认问题。
**需要逐条看：** 只要满足以下任一条。

| 原因 | 条数 | 为什么不能批量 |
| --- | --- | --- |
| 指向不明（版本省略，号对应两份不同文件） | 8 | 一个号两份文件，机器无法替 QA 选 |
| 找不到（库里没有这份文件） | 4 | 按原则 2：找不到就明确说找不到，不推测 |
| 引用已作废的文件 | 6 | 本身就是待确认问题，要人决定怎么处理 |
| 引用了旧版文件 | 1 | 同上 |
| 引用旧版药典（2020 年版） | 11 | 同上 |
| 只靠设备型号命中（低置信） | 9 | 没写文件编号，只是靠型号推出来的 |
| 泛指引用（「按相关清洁规程执行」） | 7 | 没有具体目标，由 QA 来定 |
| **合计** | **46** | |

可批量的 **150 条**（编号引用 120、药典通则 30），逐条的 **46 条**，合计 196。
这些数字会随样本或规则的调整而变，这里只是当前的数。

**补充（2026-11-04，UX-27 已作废文件默认隐藏之后）：** 已作废文件里的 19 条引用不需要确认，默认隐藏。要确认的是 **177 条**：

- 可批量 **137 条**：编号引用 107（来自 31 份文件）、药典通则 30（来自 7 份文件）。
- 逐条看 **40 条**：指向不明 6（在 3 份文件里）、找不到 4、引用已作废的文件 4、引用旧版文件 1、引用旧版药典 11、只靠设备型号 9、泛指引用 5。

上面的表格保留原样，是这条规则之前的数。第三轮线框用的是这组新数。

**批量通过前为什么要抽查（2026-11-04，UX-32）：** 批量确认是 QA 签字认可自己没逐条读过的引用，而影响清单、换版追踪都建立在这些引用上。随机抽 3 条看原句，让 QA 亲眼看到系统读得对，再点「确认全部」，过程留痕。它是让人放心、留下依据，不是靠统计查错，所以 3 条够用。只在首次导入需要。

## 关键状态

| 状态 | 在哪些页面出现 | 界面要表达什么 |
| --- | --- | --- |
| 未导入（空状态） | 首页 | 告诉用户第一步做什么 |
| 导入中 | 导入进度 | 在读什么、读到哪了 |
| 导入完成，有待处理 | 首页、导入进度 | 还有多少引用、多少问题等着 |
| **低置信** | 确认队列 | 为什么低置信（只写了型号、泛指等），和普通引用明显区分 |
| **找不到** | 确认队列、双向视图 | 明确写「库里没有 STP-GY-011」，不猜；可标为「确认库里没有」或「改指向」 |
| **指向不明** | 确认队列 | 列出这个号对应的几份文件，让 QA 选 |
| 已确认 / 已驳回 / 待确认 | 所有引用 | 一眼分清，确认能撤回 |
| 队列清空 | 确认队列 | 告诉用户做完了，下一步去哪 |
| 无筛选结果 | 确认队列、清单 | 区别于「没有数据」 |
| 问题：待处理 / 已处理 / 暂缓 | 待确认清单 | 暂缓必须写理由 |
| 导入失败（某文件读不出） | 导入进度 | **设计里要有，数据里没有**：现在样本都能读，这个状态只在界面上展示 |

## 要比较的两个版本（页面 4：单份文件的双向依赖）

- **A 独立页：** 点进一份文件，占满整个内容区。左边「我引用了谁」，右边「谁引用了我」，下面是同组成员。适合深入看。
- **B 侧栏：** 在确认队列或文件列表旁，点一份文件就在右侧展开。适合边确认边看，不用跳页。
- **怎么测：** 两个版本都做，用一个隐藏开关切换。测试时让用户完成同样的任务（例如「找出所有引用 SOP-SB-021 的文件」），比较完成时间、是否迷路、主观感受。
- **成本：** 需要做两套界面，但数据和逻辑共用。

## 功能清单

| 功能 | 优先级 | 理由 |
| --- | --- | --- |
| 批量通过 + 逐条确认 / 驳回 | **必做** | 已定 |
| 引用原文高亮（看得到在哪份文件哪一条、怎么写的） | **必做** | 时刻 1 的核心：不用跳出去就能判断 |
| 低置信、找不到、指向不明的区分 | **必做** | AI 原则 3、2 |
| 导入进度和结果摘要 | **必做** | 已定 |
| 双向依赖（A、B 两版） | **必做** | 已定 |
| 待确认清单：已处理 / 暂缓（写理由） | **必做** | 产品定义：只对 QA 可见，可分批整改，处理过程留痕 |
| 撤回确认；操作记录（谁、何时、对什么、改前改后） | **必做** | AI 原则 5；数据模型的「事件」 |
| 筛选与搜索（按文件、类型、置信度、状态） | 建议做 | 196 条不筛选很难用 |
| 改指向（把引用改成指向另一份文件） | **必做** | 处理「指向不明」「找不到」要用（已定） |
| 手工添加一条引用（直接记为已确认） | 以后 | 数据模型里有这条状态流转，但不影响主流程（已定） |
| 图形化的关系图（节点连线） | 待发散 | 35 份文件、196 条引用画成图可能很乱，第 3 步用线框比较，再决定要不要做（已定） |
| 键盘快捷键（逐条处理时按键确认） | 以后 | 好用但不影响主流程 |
| 导出待确认清单 | 以后 | 产品定义没要求 |

## 已定的四个判断

1. **批量规则：** 按上表。已经算作问题的引用（旧版药典、引用已作废文件等）放进「逐条看」，不进批量。
2. **改指向进 MVP，手工添加一条引用放后面。**
3. **导入进度是演示效果：** 阶段分步显示，数字是真的，速度放慢，让人看清系统在做什么。界面上不假装这是实时的耗时，原型说明里要写清「进度为演示效果」。
4. **关系图先放到第 3 步的线框里比较**，再决定做不做。
