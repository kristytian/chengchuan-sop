# 变更影响清单模块：功能与用户流程

状态：**已定稿**（第 2 步 · 影响清单，2026-11-03；5 个待判断问题已按建议定下，见文末）
对应旅程：时刻 2「起草人拿到影响清单，凭什么信它找全了」、时刻 3「QA 把清单导出、附进变更控制单交给负责人签字」（design/journey-scenario1.md）

## 目的

修订一份文件、或外部标准变化时，帮起草人和 QA 把「要跟着改的文件」找全，说清每份为什么在清单里、该改到什么程度，并在人确认之后导出，附进变更控制单。

**使用者：** 起草人（先确认）→ QA 文件管理员（后复核并导出）。
**原则：** AI 找问题，人下结论；每条结论都能溯源到条款；分档不一刀切；可改、可追溯（产品定义的 AI 五条原则）。

## 两个场景在这个模块里的差别

| | 场景一：修订 SOP-SB-021（02 → 03） | 场景二：药典通则 1105 修订 |
| --- | --- | --- |
| 变更源头 | 一份文件的新旧版 | 一条外部标准通则 |
| 新旧版差异 | 有：3 处文头、11 处条款，改动按词高亮 | **没有**（修订内容是虚构的，不编） |
| 受影响文件（当前数据） | 10 份：直接 9、二级 1；其中 4 份低置信 | 9 份：直接 5、二级 4；全部高置信 |
| 同组成员 | 有 1 份因同组被拉进来 | 无 |

## 页面清单（共 6 个）

| # | 页面 | 它要回答的问题 | 主要动作 |
| --- | --- | --- | --- |
| 1 | 变更列表 | 现在有哪些变更？各到哪一步了？ | 打开一个变更；发起变更（填 OA 变更控制单号） |
| 2 | 新旧版差异（仅场景一） | 这次到底改了什么？ | 逐条看改动；跳到受影响文件 |
| 3 | 影响清单 | 哪些文件受影响？轻重如何？ | 查看依据；确认、驳回、改档位；提交复核 |
| 4 | 影响项详情 | 这份文件为什么在清单里？要改哪几条？ | 看命中的条款原文；看 AI 的理由；写自己的判断 |
| 5 | 未列入说明 | 哪些文件我以为会列、却没列？为什么？ | 查看原因；必要时手工加入 |
| 6 | 清单导出 | 附进变更控制单的那一版长什么样？ | 预览；导出（导出后锁定，不再变） |

页面 4 可以是独立页，也可以是清单旁的侧栏，放到第 3 步线框里比较。

## 主流程

**起草人：**
1. 在变更列表里打开（或发起）一个变更，填变更控制单号（OA 里的号，只存文本）。
2. （场景一）看新旧版差异，确认系统找到的改动是对的。
3. 进入影响清单，看到每个受影响文件及其层级：直接、同组、二级（仅供参考）。
4. 逐项看依据：命中了哪个引用、在哪一条、原文怎么写。
5. 对每一项给出档位：必须改 / 需评估 / 仅告知；可接受 AI 建议，也可以改，改动会留下记录。
6. 可以驳回不相关的项。提交给 QA 复核。

**QA：**
7. 复核起草人的结论，特别是低置信项和和 AI 建议不一致的项。
8. 看「未列入说明」，确认系统没有漏掉本该列入的。
9. 全部确认后导出。导出的那一版锁定，附进 OA 里的变更控制单。变更进入「清单已确认」，之后接换版与培训。

## 每个影响项上要看到的信息

| 信息 | 来源 | 为什么要给 |
| --- | --- | --- |
| 文件编号、名称、版本 | 样本库 | 基本身份 |
| 层级：直接 / 同组 / 二级 | 规则 | 说明系统有多确定。二级只是参考 |
| 命中的引用：哪一条、原文怎么写 | 规则 | 溯源：这是时刻 2 的核心 |
| 置信度：高 / 低（低 = 只靠设备型号等） | 规则 | 让人知道哪些要多看一眼 |
| AI 建议的档位、置信度、理由、涉及条款 | AI 预跑结果 | 辅助，不是结论 |
| 人定的档位、谁定的、何时、改前改后 | 人的操作 | 最终结论，AI 和人的字段分开存 |
| 状态：待确认 / 已确认 / 已驳回 | 人的操作 | 起草人确认，QA 复核 |

AI 建议和人的结论在界面上**始终分开**，让人分得清哪部分是人定的。

**补充（2026-11-04，第 3 步线框后，见 UX-34，提议中）：** AI 的重点从「建议档位」改为「逐条建议怎么改」：每条命中的条款给出改成什么、依据源文件哪一条，人逐条采纳；档位由人在看完后定，AI 的档位只作参考。上表「AI 建议的档位、置信度、理由、涉及条款」一行保留，另加「每条命中条款的改法建议」和「人对每条改法的采纳结果」。

**再补充（2026-11-04，第二轮修改后）：** 每条命中的条款只有一个结论：要改（附修改要点）/ 不用改 / 待评估（附评估说明和评估需要什么），AI 预选、人确认；这份文件的档位按各条结论预选。主流程第 6 步「驳回不相关的项」在界面上叫「不相关，移出清单」，收在「更多」里；日常操作是「确认这份」和「跳过，稍后再看」。「二级」在界面上叫「间接相关 · 仅供参考」。

**补充（2026-11-05，影响评估第四轮，UX-40）：**
- 上面页面清单里的「未列入说明」不再是一页：系统看过没列入的，放进「＋ 加入一份文件」当建议；人工移出的，折叠在受影响文件列表最下面。主流程第 8 步「看未列入说明」改成：觉得有漏，就点「加入一份文件」，那里能看到系统看过但没列入的几份和原因。
- 下面功能清单里「手工加入一份文件：以后」改为**必做**：在文件库里搜任何一份加进来，写一句为什么受影响，标「人工加入」。
- 新旧版差异只用左右并排，加一个可收起的 AI 总结（新的 AI 预跑任务）；从条款里打开的是同一个视图。
- 线框见 design/wireframes/impact-list-r4.html。上面的原文保留不改。

**再补充（2026-11-05，影响评估第五轮，UX-41）：**
- 每份受影响文件的详情是「原文 + 页边批注」：原件按药厂文件格式显示，命中处标号，每个标号一条批注（要改 / 不用改 / 待评估 + 修改要点）；AI 也可以在规则没命中的地方加批注。人工加入的文件只看原件、选中加批注，没有 AI。
- 新旧版差异是两页原件并排，入口在变更标题那一行「对比 02 / 03」，用「改动 n / 14」导航。
- AI 提示「可能缺少的文件」：带依据，人定写进现有文件的批注、发起「新建一份文件」，还是不需要。
- 线框见 design/wireframes/impact-list-r5.html、new-file-r1.html。

**再补充（2026-11-05，影响评估第六轮，UX-42）：** 主流程里起草人的操作只剩「确认这份」（确认后自动跳到下一份）；「跳过，稍后再看」去掉，不确认就是还没确认。档位和「确认这份」在详情顶部右边。线框见 design/wireframes/impact-list-r6.html。

**再补充（2026-11-05，线框重新整理，UX-43）：**
- **评估时可以顺手改：** 每条修改要点可以「套用」到原文，也可以切到修订模式直接改条款，改动按修订痕迹存成这份文件的修订稿。导出后进入新加的「修订」一站，各份文件交给起草部门改完、送 OA 审批，再进换版追踪。
- **列表：** 最上面一行是「源头」（场景一点「对比 →」看 02 / 03，场景二点「打开 →」看那条标准），取代标题旁的「对比 02 / 03」。受影响的文件按「为什么在清单里」分组：引用了源文件、同组、只写了设备型号（就是上文的低置信）、人工加入；间接相关、可能缺少的文件、移出的折叠在下面。界面上不再写「直接」「低置信」。
- **AI 和人分开的显示：** AI 的建议是小灰字「AI：必须改」，不加框；人选的才是结论。
- **角色：** 上文写「起草人」的地方，界面上不再写角色，写「站名 · 状态」；不是所有厂都由起草人评估。「已定的五个判断」第 1 条「当前身份切换」改成右上角的账号菜单，演示时在里面切换账号。
- **QA 复核：** 「复核通过 / 提出意见」，意见写在某条批注上；有意见的，影响评估回到「进行中」。
- **修改记录：** 不在「⋯」里，是标题旁的「改过 n 次 ↗」；「⋯」只放下载原件、移出清单。
- 线框见 design/wireframes/03-change.html。上面的原文保留不改。

**再补充（2026-11-05，UX-44）：** 上一条第一点「评估时可以顺手改」作废。影响评估只读，只定范围：哪些文件要改、改哪几处、修改要点；原件不能改，没有「套用」。清单导出后才进「修订」：修改要点在那里逐条套用，每条「要改」都要了结（套用、自己改，或写理由不改）才算改完；评估时漏掉的，回到这里补上、导出第 2 版。

**再补充（2026-11-06，UX-47）：** 变更里改成 5 个页签（概览 · 影响评估 · 修订 · 换版追踪 · 培训），「发起」不再是一站，发起时的信息在「概览」。导出页只留结果：左边按档位列文件（不标来源），版本在标题旁「第 1 版 ▾」，只有「导出 PDF」。修订是一页：左边要修订的文件（不含源头、不按档位分组），状态未开始 / 修订中 / 已送审；每条修改要点「套用」或「不改…」。线框见 03-change.html 画面 14、15。

## 关键状态

| 状态 | 在哪些页面出现 | 界面要表达什么 |
| --- | --- | --- |
| 暂无 AI 建议（**当前所有项都是这个状态**） | 清单、详情 | 档位栏为空，写明「暂无 AI 建议」，由人直接分档；不能留空白让人以为出错 |
| AI 建议已过期（样本或提示词变了） | 清单、详情 | 灰掉旧建议，提示重新预跑；不采用旧值 |
| AI 说「无法判断」 | 清单、详情 | 明确写出缺什么信息，不硬给一档 |
| 低置信（只靠设备型号命中） | 清单 | 和高置信明显区分，提示要多看一眼 |
| 二级（仅供参考） | 清单 | 默认和直接项分开显示，轻量一点 |
| 因同组被拉进来 | 清单 | 说明理由：同组，换版时自动进入核对 |
| 人改了 AI 的建议 | 清单、详情 | 显示「AI 建议 X → 人定 Y」，QA 复核时重点看 |
| 已确认 / 已驳回 / 待确认 | 清单 | 一眼分清 |
| 导出前还有未确认项 | 导出 | 提示还有几项没确认，不能导出，或明确警告 |
| 已导出（只读） | 清单、导出 | 锁定，显示导出时间和人，之后不能再改 |
| 没有差异（场景二） | 变更页 | 说明「外部标准修订，不含条款差异」 |
| 没有受影响文件 | 清单 | 空状态，说明可能的原因 |

## 功能清单

| 功能 | 优先级 | 理由 |
| --- | --- | --- |
| 变更列表；发起变更并填变更控制单号 | **必做** | 变更是三个模块的主线 |
| 新旧版条款差异，改动按词高亮 | **必做** | 数据已有；旅程时刻 2 的前提 |
| 影响清单：层级、命中条款、置信度 | **必做** | 时刻 2 |
| 分档：接受 AI 建议 / 自己改；AI 与人的字段分开 | **必做** | AI 原则 1、3、5 |
| 逐项溯源：命中的条款原文 | **必做** | AI 原则 2 |
| 起草人确认 → QA 复核 | **必做** | 数据模型的状态流转 |
| 导出：定稿预览，导出后锁定 | **必做** | 时刻 3 |
| 修改记录（谁、何时、改前改后） | **必做** | AI 原则 5；数据模型的事件 |
| 未列入说明（泛指引用、同组成员等） | 建议做 | 旅程里「没列入的有哪些、为什么」 |
| 筛选与排序（按档位、层级、置信度、状态） | 建议做 | 场景一 10 条还好，场景二以后可能更多 |
| 手工加入一份文件 | 以后 | 补系统漏掉的，产品定义没要求 |
| 重新预跑 AI 建议（现场调用） | 不做 | 原型不现场调用模型，只读缓存 |

## 已定的五个判断

1. **起草人和 QA 两阶段：** 顶部放「当前身份」切换。起草人确认后切到 QA 复核，演示交接。
2. **AI 分档：** 界面先按「暂无 AI 建议」做，把空状态做好。界面能点之后，再用密钥跑一次 AI 预跑（约 1–2 美元），第一次完整看就有真实建议，也能验证「AI 与人分开」的显示。
3. **导出：** 做成打印友好的定稿页，带变更信息、清单、确认人和时间，页面标明「已锁定」，可打印或存成 PDF。原型不生成真实文件。
4. **二级项也分档：** 默认折叠，标「仅供参考」。
5. **分档的交互方式、影响项详情放哪：** 留到第 3 步比较线框（分档：表格下拉、三栏分组、看板拖拽；详情：独立页或侧栏）。
