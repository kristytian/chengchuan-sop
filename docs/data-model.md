## 设计原则

模型按真实系统设计，原型只实现其中一部分。五条原则都来自一页产品定义，后面每个实体都要对得上。

1. **只读快照。** 文件内容是从共享盘和台账导入的快照，系统从不写回源文件。每个文件版本都记着来自哪次导入、哪个路径。
2. **跟踪状态不是 GMP 记录。** “已发放”“已回收”只是跟踪状态，正式记录是纸质签收单和 OA。系统只存签收单编号和核销结果。
3. **AI 建议和人的结论分开存。** 引用、影响档位、培训题都有两组字段：AI 给的建议和置信度，人确认后的结论。界面上始终分得清哪部分是人定的，对应 AI 原则“AI 找问题，人下结论”。
4. **每条结论都能溯源到条款。** 引用、影响项和培训题都指向具体的文件编号、版本和条款号。找不到对象时存成“未解析”，不猜，对应“找不到就明确说找不到”。
5. **为审计追踪留位置。** 人的每个动作都写进只追加的事件记录：谁、何时、对什么、改前、改后、理由。以后加电子签名，只需要给事件挂一个签名对象。

## 状态流转

每次状态变化都写一条事件。换版和培训在真实流程里常常交叉，很多厂要求先培训后生效，所以变更状态里两者并行，不规定先后。

| 对象 | 状态顺序 | 谁推动 |
| --- | --- | --- |
| 引用关系 | 待确认 → 已确认 / 已驳回 | QA 文件管理员；人工添加的引用直接是已确认 |
| 待确认问题 | 待处理 → 已处理 / 暂缓 | QA 文件管理员；暂缓也要写理由 |
| 变更 | 影响分析中 → 清单已确认 → 换版与培训（并行） → 可关闭 | 起草人发起，QA 推进；“可关闭”只是提示，真正关闭是 QA 负责人在变更控制单上签字 |
| 影响项 | 待确认 → 已确认 / 已驳回 | 起草人确认，可改档位；QA 复核 |
| 换版任务 | 待发放 → 已发放 → 已回收 → 已核销 | 部门持有人确认收发；QA 凭签回的签收单核销 |
| 签收单 | 已生成 → 已打印 → 已签回 → 已核销 | QA 文件管理员 |
| 培训包 | AI 草稿 → 修改中 → 已确认 → 已导出 | 起草人修改和确认；导出后走现有的培训和考核流程 |

## 场景一的落点

用乳化均质机更换走一遍，检查每一步都有实体接得住。

1. **导入：** 一次导入批次读入 35 份文件和台账，生成文件、文件版本和条款。AI 运行（引用识别）给出引用建议，QA 逐条确认；7 类问题进待确认清单。
2. **修订：** 工艺员放入 SOP-SB-021-03 修订草稿（RH-500），成为一个新的草稿版本；发起变更，填上 OA 里的变更控制单号；系统算出条款差异。
3. **影响分析：** AI 运行（影响分析）沿已确认的引用和设备编号找到 9 份连带文件，生成影响项。同组规则把 SOR-SB-021-R01 拉进来；VP-QJ-003-01 只写了设备型号，标为低置信；批记录引用的 STP-GY-011、STP-GY-012 存成未解析。起草人确认后导出清单。
4. **换版：** 连带文件新版批准后，按持有记录生成换版任务，乳膏车间甲班和乙班各一组；打印签收单，签回后 QA 核销。
5. **培训：** AI 运行（培训包）从条款差异生成培训包和题目；无法出确定答案的条款单独标出（素材是 SOP-SB-021-03 草稿 4.5 里的“补加适量纯化水”）。
6. **收尾：** 任务全部核销、培训包已导出，变更显示“可关闭”；QA 负责人在纸质变更控制单上签字。全程每个人的动作都在事件记录里。

场景二只在第 2 步不同：变更的源头是外部标准（虚构的通则 1105 修订，见总控 D-12）。原型不写修订内容，没有条款差异，影响项只按引用关系推出。

## 边界与待定

三样东西刻意不进模型：

- **标准答案表：** 只用来评估 AI，单独放在样本库旁边，应用读不到它。
- **OA 和纸质记录：** 只存变更控制单号和签收单编号，不存记录本身。
- **审批流程：** 草稿到批准在 OA 里走，系统只读到“已批准”的新版本。

第 2 周要定的问题：

- [ ] **换版确认方式：** 部门扫码，还是 QA 代为登记？模型里的“确认方式”字段两种都支持，界面到第 5 周再定。
- [x] **条款怎么切：** 真实 SOP 的条款编号常常不规范。样本统一用“6.2”这样的编号；导入时切不出来的整段算一个条款。
- [x] **原型数据怎么存：** 数据打包进代码，交互状态存在浏览器里，配一个“重置演示”按钮（11/2 定，见总控 D-09）。
- [x] **一个变更有几个源头：** MVP 先只支持一份源文件或一个外部标准，两个场景都够用。
